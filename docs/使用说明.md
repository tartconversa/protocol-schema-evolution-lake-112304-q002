# 中文使用说明

本说明面向三类使用者：数据平台/数据治理人员、实验负责人、分析使用者。
所有数据均为本地合成资料，不包含真实实验室、研究人员或实验结果。

## 1. 安装与测试

需要 Python 3.11–3.14，仅用标准库。

```sh
python3 -m unittest discover -s tests -v
```

安装为包后可用 `protocol-lake` 命令；未安装时用
`PYTHONPATH=src python3 -m protocol_schema_evolution_lake.cli`。下文示例统一写短命令。

## 2. 输入资料

必选（放在同一目录，`--data` 指向它）：

* `protocols.csv`：`protocol_id, version, lab_id, effective_from, review_state, parent_version`
* `schema_fields.csv`：`protocol_id, version, field_id, name, type, unit, semantic_ref, required`
* `run_results.csv`：`run_id, protocol_id, version, field_id, value, unit, recorded_at`
* `mappings.csv`：`mapping_id, source_version, source_field, target_version, target_field, transform_note, approval_state`

可选治理文件（分别用 `--reviews` / `--conversions` / `--adjudications` 传入）：

* `semantic_reviews.csv`：`review_id, source_version, source_field, target_version, target_field, judgment, basis, reviewer_role, decided_by, decided_at, review_state`
  * `judgment` 取 `same_quantity` / `renamed_only` / `changed_meaning` / `split` / `unknown`
  * `reviewer_role` 必须为 `experiment_owner`（科学含义由实验负责人判断）
  * `review_state` 取 `approved` / `pending` / `rejected`
* `unit_conversions.csv`：`conversion_id, source_unit, target_unit, factor, offset, approval_state, approved_by, basis`
* `mapping_adjudications.csv`：`adjudication_id, source_version, source_field, target_version, target_field, effective_state, effective_note, basis, decided_by, decided_at`

字段约束：CSV 为 UTF-8（可带 BOM）、`\n` 换行；`decided_at` 为带时区 ISO 时间；
数值用十进制文本，不使用科学计数法。

## 3. 三名角色的操作

### 3.1 数据治理人员

**批准字段映射**：在 `mappings.csv` 中为映射行设置 `approval_state=approved`。
若同一映射键存在多条互相矛盾的记录，装载器会保留全部历史并报
`mapping_decision_conflict`，此时在 `mapping_adjudications.csv` 中登记正式裁定：

```
adjudication_id,source_version,source_field,target_version,target_field,effective_state,effective_note,basis,decided_by,decided_at
ADJ-001,v1,F-01,v2,F-01,approved,same,复核后确认同名同义,governance-02,2026-02-20T09:00:00Z
```

**批准单位换算**：在 `unit_conversions.csv` 中登记经批准的线性换算
（`factor`、`offset`，即 `目标 = 源 * factor + offset`）。缺失换算时，需要换算的
映射会以 `unit_conversion_missing` 阻断。

**批准兼容范围**：用 `--include-states`、`--versions`、`--target-version`、
`--fields` 决定哪些方案状态/版本/字段进入数据产品。

### 3.2 实验负责人

**判断方案变更是否改变科学含义**：在 `semantic_reviews.csv` 中为每条映射给结论与依据。

* `same_quantity`：同一量的重新测量，可合并；
* `renamed_only`：仅改展示名称，可合并；
* `changed_meaning`：科学含义改变，禁止合并；
* `split`：旧字段被拆成多个观察项，历史值需按新协议重观测，禁止行级重表达；
* `unknown`：不足以判断，保持不合并。

### 3.3 分析使用者

**选择适用于比较的数据集版本**：

```sh
# 查看账本，选版本
protocol-lake catalog --lake ./lake

# 查看某版本的可比较范围与阻断原因
protocol-lake trace --lake ./lake --name lab-shared --dataset-version v2

# 按记录追溯：原始值、换算、语义依据
protocol-lake trace --lake ./lake --name lab-shared --dataset-version v2 --run-id RUN-0012
# 按字段追溯
protocol-lake trace --lake ./lake --name lab-shared --dataset-version v2 --member v1/F-02
```

数据集里 `metrics.csv` 的 `status` 列告诉你：`cross_version_comparable` 可跨版本合并；
`version_only` 只能在本版本内使用，原因见 `reasons`。

## 4. 兼容性判定规则（按顺序）

对每条映射，裁决按以下顺序短路：

1. 源/目标字段必须已登记，否则 `dangling_reference`。
2. 源/目标字段在各实验室间名称与单位必须一致，否则 `physical_definition_conflict`。
3. 声明与物理事实核验：
   * `same` 但单位不同 → `claim_contradicted`；
   * `unit-convert` 但字段名不同、或单位本就相同 → `claim_contradicted`；
   * `split` 但只登记一个目标 → `split_incomplete`；拆分合法 → `split_requires_reobservation`；
   * `unresolved` → `unresolved_claim`。
4. 治理：裁定冲突或记录冲突未解决 → `governance_conflict`；已拒绝 → `rejected`；未批准 → `pending_approval`。
5. 语义评审：缺 → `semantic_review_missing`；待定 → `semantic_review_pending`；
   拒绝 → `semantic_review_rejected`；冲突 → `semantic_review_conflict`；
   `changed_meaning` → `semantic_change_declared`；`split` → 需重观测。
6. 换算：`unit-convert` 需要已批准的换算，否则 `unit_conversion_missing` / `unit_conversion_pending`。
7. 全部通过 → `mergeable`。随后全局检查换算环是否自洽；不自洽的连通组整组暂停。

只有 `mergeable` 的边才会把两个版本字段并入同一指标组。组内每一个成员都会按
BFS 组合出到基准版本的换算，任意一端缺路径则该组不可构建。

## 5. 发布与版本追溯

```sh
# 首次发布
protocol-lake publish --data data --name lab-shared --lake ./lake --dataset-version v1 \
  --reviews governance/semantic_reviews.csv --conversions governance/unit_conversions.csv

# 协议修订后：用新参数重建，显式替代旧版本
protocol-lake publish --data data --name lab-shared --lake ./lake --dataset-version v2 \
  --supersedes v1 ...

# 或按旧版本参数原样重建
protocol-lake rebuild --data data --lake ./lake --name lab-shared --dataset-version v1
```

行为保证：

* 已发布目录**字节不变**；替代关系与受影响分区只写进 `catalog.json` 和新版本清单。
* 同版本同内容重复发布直接复用；同版本不同内容报错，不覆盖。
* `verify` 检测人为篡改与清单外文件。
* 清单记录输入哈希、协议/映射/评审/换算/裁定指纹与构建参数，支持审计与重建。

## 6. 输出文件速查

| 文件 | 内容 |
| --- | --- |
| `manifest.json` | 发布清单：参数、指纹、文件哈希、分组摘要、替代关系 |
| `lineage.json` | 协议族血统、映射决策历史、逐组变换依据 |
| `registry_snapshot.json` | 本次使用的协议与字段快照（含原始行号与指纹） |
| `governance_snapshot.json` | 映射、评审、换算、裁定的完整历史 |
| `metrics.csv` | 每个版本字段的可比较状态与原因 |
| `compatibility.csv` | 每条映射的裁决与历史 |
| `exclusions.csv` | 未进入数据集的记录及原因（方案状态、单位不符、非数值等） |
| `issues.csv` | 装载与构建诊断（严重度、代码、对象、细节） |
| `partitions/<group>.csv` | 指标组数据行，含原始值与标准化后的度量 |

## 7. 常见问题

* **为什么我的合并没有发生？** 用 `trace` 看 `compatibility.csv` 里该映射的 `outcome` 与
  `reasons`，通常是缺评审、缺换算或声明与物理定义矛盾。
* **历史记录能自动“翻译”成新字段吗？** 仅在映射获批准、语义评审通过、换算齐备且
  用 `same`/`unit-convert` 表达时才会重表达；被拆分或语义改变的字段不重表达，
  需按新协议重观测。
* **旧数据集已被引用，协议又改了怎么办？** 用新版本重建并 `--supersedes`；
  旧版本保持原样并标出受影响分区。
* **合成资料的结论为何如此保守？** 自带 `data/` 故意让所有映射与物理定义矛盾，
  正确结论就是“无可跨版本合并指标”。正例见 `fixtures/coherent/` 与 `fixtures/adjudicated/`。
